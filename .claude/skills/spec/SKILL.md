# spec — 계획 인테이크 (구현 금지)

## 이 스킬이 하는 일
구현에 들어가기 **전에**, 목표를 또렷하게 만들고 작업을 실행 가능한 단위로 쪼개어
**계획 파일 하나**(`~/.claude/plans/<slug>.md`)를 산출한다. 그리고 멈춘다.

왜 나누나: 계획과 구현을 섞으면 목표가 흔들린 채 코드가 쌓여 되돌리는 비용이 커진다.
계획을 먼저 완결하면 사용자가 전체 그림을 검토한 뒤에 구현이 시작되므로 재작업이 줄어든다.

## 절대 규칙
- **구현하지 않는다.** 이 스킬을 도는 동안 프로젝트 코드·파일을 만들거나 수정하지 말고,
  빌드·테스트·설치 명령도 실행하지 않는다. 읽기(코드·문서 탐색)와 질문은 자유.
- 이 스킬의 **유일한 산출물**은 계획 파일(`~/.claude/plans/<slug>.md`) 하나다.
  (네이티브 plan 모드 안에서 호출됐다면, 모드가 지정한 계획 파일 경로에 쓴다.)
- 각 단계 끝에서 사용자와 **체크포인트**를 갖고 넘어간다. 혼자 4단계를 몰아치지 않는다.

## 4단계

### 1) 목표 확인
- 사용자가 원하는 것과 그 이유를 **내 말로 다시 정리**해 되짚는다.
- 내가 하고 있는 **가정**을 명시적으로 나열한다.
- **모호한 지점·미확정 사항**을 불릿으로 드러낸다 (여기선 아직 해결하지 않는다).
- 짧게. 이건 거울이지 에세이가 아니다.

왜: 이해를 되비추면 어긋남이 초반에 잡히고, 사용자에게 고칠 구체적 대상이 생긴다.
→ 확인/정정을 받고 다음으로 간다.

### 2) 인터뷰
- 1단계에서 드러낸 모호한 점을 **구체적 질문**으로 바꾼다. 선택지가 있는 질문은
  `AskUserQuestion` 으로 던지되 **추천 기본값**을 함께 제시한다(사용자가 확인만 하면 되게).
  열린 설계 질문은 자유서술로.
- **작은 묶음으로** 묻는다. 답이 계획을 가장 크게 바꾸는 질문부터. 한꺼번에 10개를 쏟지 않는다.
- 코드·문서를 읽거나 빠른 검색으로 답할 수 있는 건 **묻지 말고 직접 확인**해 사용자 부담을 던다.
- 남은 미지수가 계획을 바꾸지 않을 정도가 되면 멈춘다. 필요하면 여러 번 돈다.

왜: 사용자는 내가 볼 수 없는 맥락을 쥐고 있다. 겨냥된 질문이 그 암묵지를 명시적 요구사항으로 바꾼다.
추천 기본값을 붙이면 사용자는 판단이 아니라 확인만 하면 되어 훨씬 빠르다.

### 3) 요구사항·task 도출
- 확정된 목표 + 답변에서 **요구사항**(끝났을 때 참이어야 하는 것)을 뽑는다.
- **실행 단위(task)** 로 쪼갠다. 각 단위는:
  - 독립적으로 **검증 가능**하고,
  - 한 번의 집중 작업으로 끝낼 만큼 작고,
  - **완료 조건**이 분명하며,
  - 의존성 순서로 정렬된다.
- **비목표(out-of-scope)** 를 분명히 적는다 — 안 하는 것을 정하는 게 하는 것만큼 중요하다.
- 각 task가 **어떻게 검증**되는지 함께 적는다. 이 repo는 test-first TDD이므로 단위마다
  `test_<name>.py` 를 먼저 두는 흐름을 전제한다 (자세히는 `references/testing.md`).

왜: 완료 조건이 또렷하고 홀로 검증되는 단위여야 구현이 매끄럽다. 모호한 task가 헛수고를 부른다.

### 4) 계획 파일
- 아래 템플릿으로 `~/.claude/plans/<slug>.md` 를 쓴다. slug 는 짧은 kebab-case (예: `asr-judge`).
- 그리고 **멈춘다.** 계획 파일 위치와 첫 task를 한 줄로 알린 뒤, 구현은 하지 않는다.
  구현은 사용자가 따로 시작한다 (네이티브 plan 모드, 또는 명시적 "시작해" 지시).

왜: 계획을 먼저 완결해 사용자가 통째로 검토하게 하면, 코드가 바뀌기 전에 방향을 확정할 수 있다.

## 계획 파일 템플릿

```markdown
# <제목>

## Context
왜 지금 이걸 하는가 — 문제/필요, 계기, 기대 결과.

## Goal
한 줄 목표 + 성공 기준(Definition of Done).

## Requirements
- ...

## Non-goals
- ...

## Tasks (실행 단위, 의존성 순)
1. [ ] <task> — 완료조건: <...> · 검증: <test/실행 방법>
2. [ ] ...

## Verification
전체가 됐는지 end-to-end 로 확인하는 방법 (명령/테스트).

## Open questions
- (남아 있으면 적고, 없으면 이 섹션 생략)
```

## 기존 워크플로와의 관계
- 네이티브 **plan 모드**와 충돌하지 않는다. 이 스킬은 그 위에서 "요구사항 인테이크"를 구조화한다.
- 산출된 계획 파일은 이후 구현 단계(사람이 시작)가 그대로 따라갈 수 있게 설계한다.
- 이 repo의 구조·규칙은 `CLAUDE.md` 와 `references/`, `docs/` 를 따른다.
