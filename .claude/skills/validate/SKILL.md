# validate — 계획 대비 구현 검증 (코드 수정 없음)

## 이 skill 이 하는 일
구현은 다른 세션이 하고, 이 세션은 **독립 검증자**다. 사용자가 지정한 plan 구간의 task 마다
"계획이 약속한 것"과 "코드·테스트가 실제로 하는 것"을 대조해 판정하고, 근거와 함께
`references/validation/` 에 리포트를 남긴다. 구현 세션은 그 리포트를 읽고 고친다.

왜 직접 고치지 않나:
- 구현 세션이 같은 폴더에서 계속 편집 중이다. 검증 세션까지 파일을 건드리면 두 세션의 변경이 섞인다.
- 고치는 순간 검증자가 아니라 두 번째 구현자가 되고, 원래 무엇이 틀렸는지 기록이 사라진다.

그래서 이 skill 이 쓰는 파일은 **리포트 md 하나뿐**이다.

## 입력
- **검증 구간** (필수): 사용자가 프롬프트로 준다. 마일스톤(`M1~M3`)이나 task 번호(`task 8~12`)로 주고, 섞어 써도 된다.
  - 구간이 없으면 `git log` 커밋 메시지에서 끝난 것으로 보이는 마일스톤을 찾는다. 그리고
    "M0~M1 을 검증할까요?" 처럼 제안해서 확인을 받는다.
- **기준 상태** (기본: 현재 브랜치의 마지막 커밋): 사용자가 "작업 중인 것까지", "커밋 안 한 것도"라고 하면
  working tree 를 그대로 검증한다.

## 절차

### 0) 기준 고정
```bash
git rev-parse --abbrev-ref HEAD && git rev-parse --short HEAD && git status --short
```
- 기본 모드에서는 마지막 커밋을 임시 폴더에 꺼내 그 사본을 검증한다. 임시 폴더는 세션의 scratchpad
  디렉터리를 쓰고, 없으면 `mktemp -d` 로 만든다.
  ```bash
  snap=<scratchpad>/validate-<sha> && mkdir -p "$snap" && git archive HEAD | tar -x -C "$snap"
  ```
  이렇게 하면 구현 세션이 도중에 파일을 바꿔도 결과가 흔들리지 않고, 리포트가 어느 커밋 기준인지 분명해진다.
  검증이 끝나면 이 사본은 지운다.
- `git status` 에 구간 관련 파일의 커밋 안 된 변경이 보이면, 리포트 머리에 "이 리포트에는 반영 안 됨"으로
  그 파일들을 적는다. 그래야 사용자가 "고쳤는데 왜 FAIL 이지?" 하고 헷갈리지 않는다.

### 1) 계획 체크리스트 만들기
검증 기준 사본의 `docs/plan.md` 에서 구간 안의 task 를 읽고, task 마다 아래를 뽑는다.
- 테스트 파일·구현 파일 경로.
- 뒤에 "후 …"로 붙은 부수 작업: `ADAPTERS`/`DETECTORS`/`PROBES` 등록, `test_runner` 확장 등.
- **"완료:" 조건을 쪼갠 개별 항목.** 판정의 기준이 이것이다.
- 그 task 에 해당하는 설계 부분: "핵심 아키텍처"의 인터페이스·레코드 필드·예외 이름, Requirements,
  Non-goals, 관련 Open questions.

체크박스(`[ ]`/`[x]`)는 믿지 않는다. 구현 세션이 갱신하지 않으므로 실제 코드로 판단한다.

### 2) 자동 게이트
```bash
bash .claude/skills/validate/scripts/gates.sh <검증 디렉터리>
```
아래 검사를 한 번에 돌린다.
- pytest(skip 사유 포함), 조용한 skip, `live` 마커 남용
- ruff, import-linter(계약이 설정된 경우), 레이어 import
- 모듈 basename 유일성과 테스트 짝
- 인라인 비밀키, Non-goal 의존성, deptry

스크립트는 사실만 출력하고, 판정은 아래 기준으로 직접 내린다. 게이트 실패는 구간 밖 파일 때문일 수도 있다.
그러니 구간 task 와 관련 있는지 가려서 적는다.

게이트 결과 해석 시 주의:
- **pytest exit 4 (수집 에러)**: 공용 `tests/conftest.py` 가 import 하는 모듈이 깨지면 전체 수집이 멈춘다.
  이때는 어떤 테스트도 돌지 않은 것이므로, 구간 전체를 판정 불가로 보고 원인 파일부터 적는다.
- **deptry (M14 전)**: 아래 두 경우는 정상적으로 뜬다. 구간에 M14 가 없으면 ⚪ 참고로만 적는다.
  - 그 의존성을 쓰는 task 가 아직이라 나는 DEP002. openai 는 M2, pyyaml 은 M7, jinja2 는 M12 부터 쓴다.
  - dev 도구(pytest, ruff 등)가 DEP002 로 잡히는 경우. `[tool.deptry]` 에 dev 그룹 설정이 없어서다.
    M14 의 완료 조건("`deptry src` green")에서 다룰 일이다.

### 3) task 별 대조 — 이 skill 의 핵심
각 task 의 테스트와 구현을 **직접 읽고** 대조한다. 자동 게이트는 "돌아간다"만 알려줄 뿐 "약속대로다"는
알려주지 않는다. 시간은 여기에 쓴다.

a. **완료 조건 ↔ 테스트**: "완료:" 항목마다 그걸 실제로 검증하는 테스트 함수를 찾아 이름을 적는다.
   못 찾으면 그 항목은 미검증이다. 테스트가 있어도 아래 경우는 검증으로 치지 않는다.
   - fake 의 반환값만 확인하고 구현 코드를 거치지 않는 테스트
   - 조건을 약하게 바꾼 assert. 예: 계획은 "N+1 번째에 BudgetExceeded"인데 테스트는 예외가 났는지만 보고
     몇 번째인지는 보지 않는 경우
   - 항상 참인 assert, 예외를 삼키는 try/except

b. **계획 스펙 일치**: 이름·경로·시그니처·필드·예외·등록이 plan 과 같은지 본다. 다르면 의도된 변경인지
   근거를 찾는다. 근거는 커밋 메시지, plan.md·docs 수정, Open questions 결정 등이다. 근거가 있으면
   🔀 DEVIATION, 없으면 ❌ FAIL 후보다.

c. **설계 원칙** (plan "핵심 아키텍처"):
   - DI: 역할 패키지는 `core` 에만 의존하고, 구체 협력자는 주입받는다. 연결(wiring)은 runner/registry 만 한다.
   - Fair-ASR: 타깃 호출 수는 `BudgetedTarget` 이 센다. probe 가 스스로 세서 보고하면 위반이다.
   - target ≠ judge 를 강제한다. 비밀키는 `api_key_env` 로만 받고, config 스냅숏은 redact 한다.
   - 비결정(LLM·네트워크) 로직은 ABC/Protocol 뒤에 두고 fake 로 테스트한다. 실 호출 테스트는 `live` 마커를 붙인다.

d. **작업 규칙** (`references/code-style.md`, `references/testing.md`):
   - 타입힌트, `from __future__ import annotations`, 공개 심볼 docstring
   - 광범위 `except` 금지, 도메인 예외는 core 에 둔다
   - 새 모듈 테스트 첫머리에 `importorskip` 브레이커, `__init__.py` 재노출

e. **범위 밖**: 구간에 없는 기능을 미리 만들었는지, Non-goals(LiteLLM, rich, 병렬 실행 등)를 들여왔는지 본다.

#### 거짓 green 주의
이 repo 는 TDD 훅 때문에 새 모듈 테스트가 `pytest.importorskip("redteam....")` 로 시작한다. 구현 전에는
편리하다. 하지만 **구현 모듈 경로가 틀리거나 import 도중 에러가 나면, 테스트가 FAIL 이 아니라 SKIP 이 되어
전체가 green 으로 보인다.** 구간 안 모듈이 skip 되면 그 task 의 테스트는 하나도 안 돈 것이다. 🔴 로 다룬다.
live 가 아닌 테스트에 `live` 마커가 붙어도 마찬가지로 기본 실행에서 조용히 빠진다.

### 4) 판정
task 마다 판정을 하나만 준다.

| 판정 | 뜻 |
|---|---|
| ✅ PASS | 완료 조건 전 항목이 의미 있는 테스트로 검증됐고, 스펙·원칙 위반이 없다 |
| 🟡 PARTIAL | 동작은 맞지만 일부 완료 조건이 미검증이거나, 가벼운 규칙 위반이 있다 |
| ❌ FAIL | 계획과 다르게 동작하거나, 근거 없이 스펙에서 벗어났거나, 거짓 green 이거나, 원칙을 어겼다 |
| 🔀 DEVIATION | 계획과 다르지만 근거가 문서화돼 있다. plan 쪽을 갱신해야 하는지만 짚는다 |
| ⏭ NOT STARTED | 구현 파일이 없다 |

발견 사항의 심각도는 세 단계다.
- 🔴 차단: 잘못된 동작, 거짓 green, 원칙 위반
- 🟡 보완: 미검증 조건, 규칙 위반
- ⚪ 참고

모든 발견에는 근거(`파일:줄`, 명령 출력)를 붙인다. 구현 세션은 리포트를 믿고 움직이므로, 근거 없는 추측은
적지 않는다. 확신이 없으면 "확인 필요"로 표시하고, 무엇을 보면 확정되는지 적는다.

### 5) 리포트
- 경로: `references/validation/<YYYY-MM-DD>-<구간>-<sha>.md` (예: `2026-09-11-M1-M3-a36b642.md`).
  폴더가 없으면 만든다. 같은 이름이 있으면 덮어쓰지 말고 이름 끝에 `-2` 를 붙인다.
- 아래 템플릿을 채운다.
- 터미널에는 판정 요약표, 🔴 목록, 리포트 경로만 보여준다. 전체 내용은 파일에 둔다.
- 커밋하지 않는다. 사용자가 요청할 때만 커밋한다.

## 하지 않는 것
- 코드·테스트·plan.md·docs 수정. 고칠 게 보여도 리포트에만 적는다.
- `pip install` 같은 환경 변경. 의존성이 없어 게이트가 못 돌면 그 사실을 리포트에 적는다.
- 실 API 호출(`pytest -m live`, 실제 엔드포인트로 `rt run`). 비용이 들고 유해 응답이 생길 수 있어서,
  사용자가 명시적으로 요청할 때만 한다.

````markdown

- 커밋 안 된 변경: 없음 | <구간 관련 파일 — 이 리포트에는 반영 안 됨>
- 종합: ✅ <n> · 🟡 <n> · ❌ <n> · 🔀 <n> · ⏭ <n> → **<한 줄 결론>**

| task | 대상 | 판정 | 핵심 사유 |
|---|---|---|---|

## 자동 게이트
| 게이트 | 결과 | 비고 |
|---|---|---|
| pytest | <passed/failed/skipped 수> | |
| 조용한 skip | <없음 / 모듈 목록> | |

### task <n> — <제목> : <판정>
- 완료 조건 대조

## 계획과의 차이
- <무엇이 다른지> — 근거: <커밋/문서>. 제안: plan.md 갱신 | 구현을 계획대로 되돌림

## 구현 세션 전달용 수정 요청

```

1. 🔴 <파일:줄> — <무엇을 어떻게>  (plan 완료 조건: "<원문>")
2. 🟡 ...
수정 뒤 `python -m pytest -q -rs` 에서 구간 모듈의 skip 이 0 인지도 확인해줘.
```
````
